## Design

- The sidebar presents one bounded navigation stack.
- Opening a root destination starts a new stack and replaces any older root stack.
- Selecting a related Task pushes its Task Detail.
- Selecting a Task that already appears earlier returns to that retained destination and removes every later destination.
- Returning to an earlier Task silently discards unsent input retained by removed later destinations.
- Dependency Add pushes the ordinary New Task form with its originating relationship preconfigured and hidden.
- Inbox Previous and Next replace the current Inbox Task and do not add history.
- X closes the complete stack.
- Back returns to the preceding destination.
- Back at the root closes the sidebar.
- Back is hidden at the root.
- The header keeps X before Back and uses the existing icon-control presentation.
- The stack has no Forward action.
- The stack retains at most 50 destinations.
- Pushing a 51st destination preserves the root and silently evicts the oldest non-root destination and its retained interface state.
- Only the current destination remains mounted and live.
- Earlier destinations retain only bounded interface state. They do not keep loading, observing, subscribing, or extending query lifetime.
- Ordinary inactive Task Detail queries keep the app's existing time-based cache behavior.
- Back restores scroll position, description expansion, the selected Comments or Activity tab, unsent Task title/body edits, unsent new-comment text, and one edited-comment draft.
- Back does not restore unfinished Question responses, server projections, query pages, loading state, mutation state, or subscriptions.
- Restored Task Detail refreshes server-authoritative data and layers retained unsent Task/comment drafts over it.
- An incoming focus request applies only when that Task destination is first opened. Back restores the saved viewport without replaying the original focus request.
- Scroll restoration creates one typed pixel-offset request with a distinct request key after refreshed rows mount. `VirtualizedInfiniteList` applies each request once through TanStack Virtual, renders the range at the nearest available position, and lets ordinary edge-driven load-more run from that restored range. It does not load pages only to reconstruct an old viewport.
- A current Task Detail that receives a typed missing-Task result immediately goes Back without showing stale Task content.
- A current Project Edit that receives the typed Project-missing result immediately goes Back instead of retaining Retry forever.
- Every other Project-bound sidebar destination owns the same behavior only when one of its existing required Project reads or mutations returns the typed Project-missing result. The implementation audit covers New Task, Project-linked Workflow Create, Link Workflow, and project-scoped Workflow Editor; a destination with no required Project signal remains unchanged.
- Successful deletion initiated from the current Project Edit closes that Project Edit root even when Home remains the visible screen. If the Project Edit was replaced before success settled, the replacement sidebar remains unchanged.
- External Project deletion invalidates the mounted destination's data. A current destination that then receives typed Project-missing dismisses itself; external deletion does not directly close or inspect an unrelated sidebar.
- If a missing Task- or Project-bound destination is the root, its Back closes the sidebar.
- If Back reveals another missing retained destination, that destination performs the same check and goes Back again. This lazily skips missing retained destinations without a history scan.
- Missing-destination Back does not wait for restored data or a retained-state snapshot. Back discards the missing current destination, so it captures nothing.
- Task and Project deletion do not otherwise alter sidebar history. The sidebar receives no deletion event and knows no Task or Project identity.
- Leaving the Desktop screen that owns a root sidebar closes that root stack unless another root sidebar has already replaced it.
- Every root sidebar belongs to an explicit screen or app owner. Each owner setup opens a fresh root handle, and that setup's cleanup synchronously releases exactly that handle. StrictMode effect replay may therefore release R1 and open fresh R2; R1 remains permanently stale, the final R2 remains live, and actual owner teardown resolves the current lifecycle once as `released` before queued completion can run.
- Opening an unrelated root sidebar replaces the prior stack. Cleanup belonging to the prior screen cannot close the replacement.
- Once Push, replace, Back, close, or root replacement is accepted, completion from the outgoing destination cannot change the accepted stack even before the UI rerenders or unmounts that destination.
- Every destination-originated close is scoped to that destination's mounted-page capability and returns only generic accepted/no-op. A stale ordinary New Task, Project Delete, Workflow Create, Link Workflow, Workflow Inspector, Task/Project missing, or Pop-out callback cannot settle, close, or otherwise mutate a replacing root or its pending lifecycle.
- Browser URL text and browser-history behavior are not part of the Desktop product contract.
- Related-Task selection and Dependency Add remain unavailable while the current Task title/body or add/edit-comment save is pending. Relationship Remove keeps its existing independent availability.
- Leaving a Task Detail while one of its saves is pending uses the ordinary discard/close behavior. Later settlement does not restore or reopen it.
- New Task has no Cancel button and does not show Dependencies.
- Before submission starts, Back from New Task discards the form and restores the preceding destination, and X discards it and closes the stack.
- Unsubmitted New Task Back does not require a snapshot because the discarded form is not reachable through Forward.
- Only while a related New Task request is pending, header Back and X are unavailable. Ordinary New Task never acquires this pending-exit lock.
- Related New Task atomically creates the Task and relationship.
- Current success replaces New Task with the created Task Detail and leaves the originating Task directly behind it.
- Current failure releases the related pending-exit lock and preserves the ordinary New Task recovery path.
- Screen change or root replacement remains legal while related creation is pending. If success or failure arrives after that replacement, the Task and relationship outcome remains authoritative and the replacement sidebar does not change.
- Pop out opens only the current Task Detail.
- Current pop-out success closes the originating stack after the separate window opens.
- Pop-out success after that destination or root stack was replaced leaves the separate window open and does not close the replacement.
- Pop out and X keep the approved silent-discard behavior for unsent input.
- Disconnect and reconnect preserve the stack and retained interface state. The current destination uses its ordinary reconnect and refresh behavior.
- Push and Back use a quick horizontal transition and respect reduced-motion settings. X keeps the existing whole-sidebar close transition.
- KENT-356 does not add browser-route migration, server/worktree changes, test timeout changes, query-cache ownership, existing-Task dependency search, or Task upsert.

## Architecture

- Treat merge-base `c945238c9` as the implementation starting point. Do not recover the superseded provider, TanStack-history wrapper, destination membership fields, deletion coordinator, route-transition owner, route test harness, scoped admission state machine, or history-wide invalidation code from branch history.
- Keep `SidebarProvider` generic. It owns one immutable in-memory stack of generic destinations and retained snapshots, the existing pending root result, width profiles, and presentation phase. It imports no Task, Project, Board, Workflow, query, mutation, deletion, or router feature module.
- Implement only four generic stack commands: Push, replace current, Back, and close. Back at root delegates to close. Push performs branch truncation, injected equality-based return-to-earlier, and root-preserving capacity eviction in one state transition.
- Keep feature equality outside sidebar code. App composition supplies one typed destination policy that can compare destinations and narrow retained snapshots. The generic stack consumes that policy without inspecting destination variants or strings.
- Keep stack positions, private remount mechanics, and one current-page registration private to the provider. The generic page host creates the registration immediately when it mounts, before destination data is ready. It contains one private mutable capability cell, header Back/X availability, an optional capture slot, and capability-scoped Push, replace, Back, and close. No lifecycle, entry, activation, route, deletion, operation identifier/token, or feature result appears in app-facade or feature contracts.
- Separate navigation capability from retained-state capture. Back/X availability controls only the rendered header controls; it does not delay navigator creation or block destination-owned missing Back. Task Detail installs the optional capture slot only after restored data is ready. Missing Task/Project destinations and unsubmitted New Task can navigate Back while the slot is absent.
- Determine the generic transition shape before changing currentness. An append Push retains the outgoing entry and therefore must synchronously resolve a present capture slot first; if capture is absent or unavailable, reject Push with the capability still active. Once append Push is accepted, revoke the outgoing capability and commit its captured snapshot plus the new entry. Same-destination return-to-earlier, replace, Back, close, and root replacement discard the outgoing page, so they synchronously revoke and commit without capture.
- Give the mounted page a navigator whose Push, replace, Back, and close methods read that private capability cell. Page close returns one generic `accepted` or `stale` outcome; accepted close revokes synchronously, settles its owning root with generic `closed`, and begins the existing close presentation. Root replacement settles the prior root as `replaced`; screen release settles it as `released`. These generic lifecycle reasons are the complete root result contract. Accepted generic transitions and root teardown are the only semantic writers that change the cell from active to revoked. Registration setup never writes an existing cell back to active. React effect cleanup never revokes the cell; it may compare-and-clear only its own capture/availability registration, and replay setup reinstalls that registration without changing capability state. A newly mounted component instance, including A after A→B→A, creates a fresh active cell. Do not add IDs, epochs, revisions, cancellation signals, owner objects, or conditional-current method families.
- Require every page-host removal that can leave `SidebarProvider` alive to result from an accepted generic transition/root release, which has already revoked the outgoing cell. Whole-provider/app unmount leaves no surviving stack owner; explicit app-owner release settles/revokes the root without using provider/page effect cleanup as a semantic transition.
- Keep asynchronous ownership in destinations. Related New Task uses scoped replace and never closes the root. Ordinary root New Task uses scoped close. Workflow Create and Link Workflow use scoped close and perform their existing follow-up navigation only when close returns `accepted`; Workflow Inspector missing-node and Pop out use scoped close; Task Detail and audited Project-bound destinations use scoped Back after the applicable typed missing result. The provider does not know which asynchronous operation produced a page operation.
- Add one generic root-owner hook/boundary. Every effect setup opens one fresh scoped root handle and owns that immutable handle, its generic lifecycle Promise, and one setup-local lifecycle observer closure. Use one boundary per durable screen/app owner rather than scattered release refs. Board, Home, Workflow Library, and the app-level Attention Notification controller receive explicit owners; descendants request roots through that owner. Page-internal Task Detail, Inbox, Link Workflow, and Workflow Editor movement uses the mounted-page navigator instead of opening a root.
- Make root-owner teardown symmetric and synchronous. Cleanup first marks only that setup's lifecycle observer inactive, then synchronously calls release on exactly that setup's root handle. Release immediately revokes the root/page capability and settles the lifecycle exactly once as `released`; if `SidebarProvider` survives, the same generic root transition removes that root, while whole-provider/app teardown settles and revokes the root object without scheduling a React state update. A lifecycle settlement observed after cleanup is ignored by that inactive setup-local closure.
- StrictMode replay follows ordinary effect semantics: open R1 → mark R1's observer inactive and release R1 → open fresh R2. R1 is permanently revoked and cannot be reused or reactivated; R2 is the live root after replay. A changed request likewise cleans up and releases Rn before its next setup opens fresh Rn+1. Event-driven Home and Attention Notification roots open after initial replay and their owner synchronously releases their exact handles on teardown. The release handle and page close are idempotent after settlement, so invoking either stale capability cannot settle twice. Do not add deferred schedulers, cancel flags, IDs, epochs, or handle-reuse paths.
- Split authority by caller. Screen code receives root open/release and the generic root lifecycle outcome. Shell code receives current X, phase, and sizing. `SidebarDestinationView` and feature destinations receive only the mounted-page navigator. Delete `SidebarNewTaskResult`, `SidebarTaskDetailResult`, `SidebarWorkflowResult`, provider-global result settlement, and the obsolete submitted-result Board route helper/test. Provider-global `resolveSidebar` or `closeSidebar` must not be passed into destination dispatch or exported as page-facing authority.
- Board selected-Task opening uses the generic root lifecycle only. Task deletion mutation and project subscription paths do not call sidebar code. Removing every selected-Task deletion hook/coordinator is required.
- Give `ProjectDeleteButton` the mounted-page navigator through destination-owned Project Edit header composition, and remove Project-specific header selection/imports from the generic shell. When its own delete mutation reports success, it invokes scoped close for that mounted Project Edit and then calls `completeProjectDeletion` for query cleanup, stored-route cleanup, visible navigation, and toast behavior. Remove sidebar parameters and imports from `completeProjectDeletion`; it owns no close authority.
