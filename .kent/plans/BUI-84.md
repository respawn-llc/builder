Design

- Treat the general filtered task collection as its own task-list read model. The board read model owns board metadata and board-column cards; it does not absorb `ListTasks`.
- The workflow orchestration layer depends on narrow board, task-list, task-detail, activity, and attention read-model interfaces. The focused modules are composed once at server startup rather than hidden behind one broad workflow-view dependency.
- Pagination cursors are ephemeral continuation data, not a migration concern. Preserve each list's ordering and continuation behavior within the current contract, but add no cross-upgrade compatibility path for cursors issued by an older server contract. Raise the server protocol version for the actual attention/task-detail contract cutover.
- A cohesive internal task-facts/DTO projector owns authoritative task summary, status, available actions, effective placements, and shared placement/run/transition/comment DTO conversion. It is independent of every endpoint module; task detail, board, task list, and activity depend on it, and no endpoint read-model module depends on another endpoint read-model module.
- Support exactly two attention read contracts: one global cursor-paginated list for Inbox and one non-paginated list for a task. Remove project-scoped attention; current desktop code only requests the global list and no project-scoped consumer was found.
- Remove embedded attention items from core task detail. Keep the unresolved-attention count used by `kent task show --json`, but derive that scalar with a generated database query. Loading core task detail must not resolve question prompt payloads or read transcript pages.
- Task attention remains non-paginated without a new numeric server cap. Its boundedness is treated as inherent to unresolved attention produced by current workflow execution, not as a general collection that can grow independently.
- Review challenged the lack of an enforced bound; the user explicitly rejected pagination or a new server-enforced maximum and reaffirmed the non-paginated contract.
- Reading the newest active transcript segment in the task-attention read is intentional. The optimization target is the CLI command and core task-detail response: both stay database-backed and fast, while the desktop task-detail page starts its independent attention read in parallel and progressively reveals attention controls when that read completes.
- Independent attention loading never blocks or disables core task detail. The attention area owns a local loading state, applies an Inbox-requested focus after the target item arrives, and surfaces a local retryable error if attention loading fails.
- Apart from the explicit attention/task-detail cutover, preserve existing response behavior, ordering, and pagination semantics.

Architecture

### Module shape and composition

- Keep one `server/workflowview` package so the split does not require exported persistence rows, DTO helpers, or circular subpackage dependencies. Replace the broad behavior-owning `Service` with focused concrete modules; production files may be split further by internal helper concern, but every production file stays below 700 lines.
- Add one supporting definition-projection module. It reuses `workflowstore.Store.GetDefinition` as the canonical domain-definition loader, projects that domain definition to the existing server API definition, derives node kinds and wiring once per request, and supplies the same immutable definition snapshot to board, task-list, task-detail, activity, and attention modules. This removes the duplicate raw-row definition assembly and the API-to-domain reconstruction currently inside `workflowview`.
- Add one pure task-facts/DTO projection collaborator that contains no persistence, endpoint orchestration, pagination, prompt, transcript, Git, or clock dependency. Its typed task-facts input contains the persisted task record, decoded status record, current placements, current runs, and definition snapshot; its output contains summary, status, actions, done state, and effective placements. Its DTO operations accept one typed placement, run, transition-plus-edges, or comment input plus the required definition/session-name facts and return the corresponding server API DTO.
- The board module owns board selection, workflow picker projection, board groups/columns/counts, board-card batching, board-card ordering, and its bidirectional cursor codec. It depends on definition projection and the pure task projector, never on task detail.
- The task-list module owns scope resolution, filtering/sorting validation, query fingerprints, matching-workflow cardinality, generated task-list queries, and task-list cursor encoding. It depends on definition/column projection and the pure task projector's status decoder, never on task detail or board.
- The task-detail module owns only task lookup by UUID/short ID, core detail loading/orchestration, execution-target/worktree projection, and source-workspace loading. It delegates all task facts and placement/run/transition/comment DTO conversion to the pure task projector and has no dependency on board, task list, activity, attention, pending prompts, or transcripts.
- The activity module owns activity cursor parsing/encoding, activity-row retrieval, batched source loading, newest-first ordering, and activity-item orchestration. It depends on definition projection and the pure task projector, never on task detail or attention.
- The attention module owns both approved contracts: the global cursor-paginated Inbox feed and the non-paginated task feed. It also owns attention candidate projection, validation-blocker projection, pending-question resolution, prompt-snapshot lookup, newest-active-segment fallback, and the global attention cursor codec.
- Do not retain a forwarding `workflowview.Service` compatibility facade. `server/workflowsvc` defines caller-owned narrow interfaces for definition, board, task list, task detail, activity, and attention, grouped in a constructor dependency value whose fields are validated once. `server/core` constructs every concrete module and shared projector once and injects those capabilities. The finalizer receives a narrow live projection seam only for pending publication; resolution is driven by immutable projections returned from committed workflow-store mutations.
- Pass stable collaborators at construction: metadata queries to modules that read metadata, the workflow store to definition and pending attention projection, the pure task projector to detail/board/task-list/activity, the role resolver to board and attention, the Git inspector to task detail, and transcript/pending-prompt providers only to the frontend attention module. Do not add generated-query interfaces or test-only hooks; module tests use real isolated metadata/workflow stores and production constructors.

### Authoritative projection data

- Introduce an internal immutable definition snapshot containing the domain definition, projected API definition, and node-kind index. A request may share this snapshot across its module operations, but no process cache is added; persisted metadata remains authoritative.
- Keep one pure task-facts/DTO implementation independent of endpoint modules. Lock parity at this seam with table-driven tests that feed identical typed inputs from detail, board-card, and task-list scenarios and require identical status/summary/action/effective-placement results. No module copies status precedence, attention-kind parsing, cancellation placement synthesis, action derivation, or placement/run/transition/comment conversion.
- Add one generated-SQL-backed workflow-attention candidate relation as the authoritative database projection for pending approvals, waiting questions, actionable interrupted runs, and workflow validation candidates. Non-applicable identifiers are SQL `NULL`, not empty-string absence sentinels. Generated queries over this relation provide:
  - the global ordered candidate page,
  - all task-bound candidates for one required task ID,
  - the exact unresolved task-attention count used by core task detail,
  - actionable interrupted-run IDs by required task ID,
  - actionable interrupted-run IDs by required workflow ID across all linked projects,
  - one approval candidate by transition ID,
  - and one actionable interruption candidate by run ID.
- Remove the current duplicated specialized attention predicates and optional empty-string project/task filters. Validation candidates have no task ID and therefore cannot enter the task feed or task count. The count query never resolves question text and never opens a transcript.
- Distinguish two projection semantics:
  - **pending projection** is ID-addressed lookup against the live candidate relation and is used only to publish attention that is currently pending/actionable;
  - **resolution projection** is a full immutable approval/interruption snapshot materialized by a workflow-store mutation transaction before it changes or deletes the qualifying rows. It contains project/workflow/task/session routing facts and, for interruption, the run occurrence timestamp/reason/detail needed after commit.
- Add transaction-scoped projection helpers over the generated relation/store records. Approve, complete, manual-move, resume, task cancel/delete, and workflow delete transactions capture every attention item they resolve and return those snapshots in their typed results. Workflow deletion extends its existing pre-delete approval projection pattern to interrupted runs across all linked projects.
- Frontend attention feeds and pending finalizer publication may use live candidate lookup. Lifecycle resolution never pre-reads IDs in `workflowsvc`, never scans global/task feeds, and never queries a candidate after mutation.

### Read paths

- `GetWorkflow` calls definition projection directly.
- Board reads linked workflows and project activity, obtains one definition snapshot per linked workflow, derives validation/picker facts, then reads board counts or a bounded card page. Card pages batch placements, runs, and statuses before projecting cards through the pure task projector; no per-card queries are introduced.
- Task list resolves project/workflow scope, obtains a definition snapshot only for workflow-narrowed requests, validates column keys, executes the existing generated keyset query, decodes row status through the pure task projector, and emits the same response ordering and cursor semantics.
- Core task detail loads the task, definition snapshot, placements, runs, transitions, comments, project/workspace facts, execution target, and database attention count, then delegates pure fact/DTO conversion. It never calls another endpoint module, attention projection, pending-prompt state, or transcript readers. All three lookup selectors converge on this same path after resolving task identity.
- Activity loads its requested page plus one row, batch-loads referenced comments/transitions/edges/runs/session names, and delegates item DTO conversion to the pure task projector without calling task detail or attention endpoints.
- Global attention pages directly over the global candidate relation. Candidate projection may discard a workflow-validation candidate that is no longer blocking; the existing over-read/drop-and-continue loop remains local to this module so the returned page is filled without in-memory pagination.
- Task attention first validates and resolves the required task, loads all task-bound candidate rows, resolves question payloads from live pending prompts or the newest active transcript segment, projects items, and returns deterministic newest-first order without a page cursor.
- Workflow-store mutation transactions capture full approval/interruption resolution projections before applying state changes or deleting rows, commit state and snapshots atomically, and return the captured projections. `workflowsvc` passes those values to the finalizer only after a successful commit; there is no service-level attention preflight or TOCTOU window.
- For pending publication, the attention finalizer requests exactly one live approval projection by transition ID or one live interrupted-run projection by run ID. For resolution, it accepts the captured projection value directly, so a fresh finalizer with no in-memory scope can publish the correctly scoped resolved event without post-mutation storage lookup.
- Every production consumer of `CompleteRunResult`/`ManualMoveResult`—workflow service orchestration, runtime completion, and script-runner completion—must forward captured approval/interruption resolution projections after commit. Bare interrupted-run IDs remain valid only for the separate publication of newly interrupted pending attention; bare transition/run IDs are never used to resolve prior attention.
- Desktop task detail starts core detail, task attention, activity, and comments independently. Core detail gates the shell; task attention uses its own query key and local loading/error/retry state. Inbox-requested focus is applied only after the matching attention row arrives. Workflow-event and mutation invalidation refresh both core detail and task attention without collapsing already-rendered detail.
- `kent task show` continues making only the core task-detail request and reads the new scalar attention count; it does not call task attention or traverse transcript data.

### Contract cutover

- Keep the two existing RPC method identities: global attention list and task-attention list. Remove project scope from the global attention request; remove the project identifier from its cursor payload because the feed is always global.
- Remove embedded attention items from `WorkflowTaskDetail` and add a non-negative unresolved-attention count. Update response validation, shared client decoding, CLI projection, desktop models/schemas, fixtures, and callers atomically.
- Add a dedicated desktop client method/query for task attention; the global Inbox client method no longer accepts a project argument. No project-scoped compatibility route or request shim remains.
- Raise `shared/protocol/version.json` for the request/response break. Apart from these explicit changes, retain existing DTO fields, item ordering, status/action meaning, error identities, and task-list/board/activity cursor behavior. Pagination cursors remain ephemeral runtime continuation data and receive no cross-version migration layer.

### Failure paths and authorized exceptions

- Constructors reject missing required collaborators before the server starts. Public request validation remains at the workflow-service/API edge, and focused modules also reject invalid direct interface calls so interface-level tests observe production behavior.
- Database, definition, projection-invariant, and context-cancellation errors propagate through the focused interface that encountered them. Unknown attention/activity kinds, malformed generated JSON, missing batched source rows, or omitted task status rows remain fail-fast invariant errors with identifying context.
- Pending-question resolution retains the current fallback item when neither live prompt state nor transcript recovery yields the original prompt; a failed task-attention read remains local to the task-attention UI and never makes core task detail unavailable.
- Failure to materialize a resolution projection aborts and rolls back the owning workflow-store mutation. After commit, notification publication remains best-effort and uses only the returned immutable projection; it never re-queries deleted or no-longer-pending rows.
- User-authorized review exception: keep task attention non-paginated without a numeric cap or fail-fast maximum; do not add pagination or an enforcement path in BUI-84.
- User-authorized scope exception: preserve the existing server-owned activity and attention display strings unchanged during this split. Do not widen BUI-84 into typed/localized copy migration.
- User-authorized scope exception: preserve task detail's existing behavior when managed-worktree Git identity inspection fails—omit the derived current branch and keep the rest of task detail available rather than adding diagnostics or failing the request.
- User-authorized scope exception (2026-07-19): preserve the existing canceled-board fallback's empty synthetic placement ID during BUI-84. Replacing that sentinel with a typed persisted-vs-synthetic placement model is tracked separately as `KENT-306`.
