## Recon

- Current runtime control surface is split across server services:
  - `server/runtimecontrol` owns most model/transcript mutation entry points (`SubmitUserTurn`, shell submit, compaction, settings updates, queue/discard prompt-history, interrupt, goals).
  - `server/runtimecommand` already models command-like execution adapters and goal-specific command authority.
  - `server/promptcontrol` handles direct ask/approval answer submission.
  - `server/workflowsvc` handles workflow task operations (`ApproveWorkflowTask`, `CompleteWorkflowTask`, question answer) separately from runtime control.
  - `shared/apicontract` and `shared/protocol/handshake.go` define service/route boundaries that currently keep runtime commands, live control, prompt responses, and workflow actions on distinct services.
- Existing API/runtime route mapping indicates command-like runtime ops are currently not on one queue yet:
  - `server/transport/gateway_unary_handlers.go` maps all runtime control ops (`runtime.*`) to `RuntimeControlService`.
  - Live control routes (`runtime.liveSteer`, `runtime.liveStop`, `runtime.liveWait`) map to `RuntimeLiveControlService`.
  - Prompt answers (`ask.answer`, `approval.answer`) map to `PromptControlService`.
  - Workflow task commands map to `WorkflowService`.
- Runtime ordering substrate exists but is operation-key scoped (`runtimeops`):
  - `server/runtimeops` (`coordinator.go`, `coordinator_ledger.go`, `coordinator_commit.go`) provides reconciliation barriers, exact-operation state transitions, cancellation/waiting, and commit mutation support.
  - `server/runtimecontrol/service*.go` uses `runtimeops.Do` and an internal coordinator for operations keyed by `operation_ref`.
  - No global session FIFO command queue is currently obvious from current naming/flow.
- Reconciliation/memoization (do not delete now):
  - `server/runtimecontrol` and `server/promptcontrol` already use `requestmemo` request-level dedupe/replay tables (for idempotency/reconnect safety).
  - `submit user turn` and related paths call `runtimeops` and request memo wrappers; this is separate from queueing-by-session authority currently required.
- Runtime execution boundaries and existing ordering semantics to preserve:
  - `server/sessionruntime/authority_execution.go` has exact-scope execution APIs and prompt resolution.
  - `sessionruntime.ExecutionScope.Resource()` succeeds only for Agent scopes. Script scopes deliberately have no Session resource and cannot target a per-Session Runtime Command queue.
  - `SubmitPromptResponse` resolves only active execution scope.
  - `ResolvePendingWorkflowPrompt` and `SubmitPromptResponseForScope` enforce exactness for pending asks/approvals.
  - `server/runtime/tool_executor.go` live Agent Workflow completion currently occurs through runtime execution path (`CurrentNodeExecution.Controller.CompleteCurrentNode`) and emits completion via runtime event stream. Script finalization calls the Workflow controller without a Session model/transcript mutation and remains a direct Workflow-domain operation.
- Background shell ownership already outlives Agent execution:
  - `shell.Manager` retains the process after a tool returns `Backgrounded`;
  - its immutable snapshot retains owner Session, Activity ID, and execution correlation including resource generation;
  - `sessionruntime.Authority.routeBackgroundEvent` already rejects a missing or successor resource generation before calling `Engine.HandleBackgroundShellUpdate`.
  `Manager.Start` currently emits `EventBackgrounded` synchronously through a process-global `func(Event)` hook before returning the backgrounded tool result, while terminal `EventCompleted`/`EventKilled` publication is serialized by the process `interactMu` until the initiating `Start`/`WriteStdin` call returns. Because that hook cannot return a steering result, the cutover must remove transition publication from it: `Start` returns a typed pending background-transition payload to the shell tool adapter, while the global hook remains terminal-only.
- Runtime command types and validation already present:
  - `shared/serverapi/runtime_control.go` defines request types for setting session state, append committed entries, compaction checks, user turn/shell submit, queue operations, interrupts, and all goal mutations.
  - Request validation already validates `operation_ref`, session/request ids, and command-specific constraints pre-dispatch.
- Command-family surface points likely impacted by unified FIFO ordering:
  - User input: `RuntimeSubmitUserTurn` (model-visible chat mutation + queue behavior when run active).
  - Steering: `RuntimeLiveSteer` currently queues directly on active run; spec says steer applies at next agent step.
  - Queue submit: `RuntimeSubmitQueuedUserMessages` currently records queued user flushing into runtime state.
  - Workflow completion: workflow svc/ runtime completion tool path touches model-visible state and is likely session-scoped.
  - Goal set/pause/resume/clear/complete go through goal authority and runtimecontrol wrapper.
  - Technical input: shell command submit and context compaction/recording.
- Potential parallel ordering sources to audit during implementation:
  - `runtimeops` operation-key serialization can remain for operation-level correctness, but it is not session FIFO.
  - `RuntimeLiveControlService` live prompt/stop/wait path bypasses runtime control queue.
  - `PromptControlService` answers are direct runtime responder calls.
  - `WorkflowService` task completion/approval/answers can currently mutate runtime-visible state without runtime command authority.
  - Existing process/session services manage non-runtime domains and should stay out of session command ordering.
- Relevant specs to anchor behavior:
  - `docs/dev/specs/core-runtime-tools.md` (runtime authority, exact execution scope, queue/steer boundaries, question/answer rules, no replay).
  - `docs/dev/specs/terminology.md` and `docs/dev/specs/workflow-orchestration.md` for scope vocabulary and exactness language.
- Existing tests to likely reuse or refactor for recon proof and FIFO/cross-session safety:
  - `server/runtimecontrol/*_test.go` for submit/shell/compact/goal/interrupt/queue command behavior.
  - `server/runtimeops/coordinator_test.go` for operation-level ordering and cancellation semantics.
  - `server/promptcontrol/service_test.go` for direct prompt answer exact-scope behavior.
  - `server/workflowsvc/current_node_completion_test.go` and related workflow service tests for runtime-visible workflow completion/order.
  - Transport/service contract tests that enforce route/service ownership boundaries.

## Design

- The server owns one FIFO Runtime Command queue for each admitted Session. Commands that target an Agent Exact Execution Scope capture that scope and revalidate it when they run, so a stale command fails without mutation instead of reaching a successor execution. Dormant Goal changes remain the specified direct exception.
- A Runtime Command that starts long-running external work first registers a blocked structured owner and continuation. Its FIFO turn may then atomically apply the prerequisite mutation and release that owner. The external work does not block the Session queue. Each intermediate or terminal authoritative effect reuses the continuation to join the queue at the then-current tail, without reserving the command's original position. Commands accepted while the work runs may therefore complete first, and every re-entered stage revalidates its target so stale results fail without partial mutation.
- Automatic after-Turn Queue follow-up remains inside the originating Agent Exact Execution Scope, `ExecutionHandle`, and root continuation. The originating idle `SubmitUserTurn` returns its first submitted turn's assistant/error through a separate typed milestone; accepted Queue or Goal continuation keeps the scope owned after that public result and releases it only after all same-scope work reaches a terminal outcome.
- The authority remains Session-only. Live Agent-Session Workflow completion uses it; Script finalization and idle Workflow completion remain direct Workflow-domain operations. A backgrounded shell process transfers to `shell.Manager`; only later Session-visible events and notices acquire Session-resource queue ownership, so neither a Script nor an unbounded process lifetime creates another queue or pins an Agent-scope permit.
- Transition-to-background publication and tool-result persistence form one runtime-owned shell result. The shell handler only returns model output plus opaque pending-transition metadata. Runtime reports backgrounding success only after one ordered stage commits both the transition event and tool completion; if that stage does not commit, the manager aborts and joins the pending process and the shell operation returns the failure.
- The long-running side-effect ordering decision remains task-local in this plan; no owning product specification is changed in this Design stage.

## Architecture

### Ownership and lifecycle

- Expand `server/runtimecommand` into the single process-local Runtime Command authority. It owns a registry of admitted Session queues and the typed adapters already represented by `ExecutionAdapter` and `GoalAuthority`; `server/runtime`, `server/runtimecontrol`, and Workflow code become producers or appliers, not alternate ordering owners.
- Bind one queue to each admitted Active Session Runtime generation, identified internally by `runtimeids.SessionResourceRef` rather than a bare Session ID. `sessionruntime.Authority` still owns resource and Exact Execution Scope lifecycle. It admits and binds the queue after the Engine is built but before the resource becomes Ready, and closes and joins that queue before the Engine is closed. A replacement resource generation receives a new queue, so accepted work can never cross into a successor runtime.
- Compose the Runtime Command authority before `sessionruntime.Authority` and pass it through a narrow resource-command lifecycle interface declared outside `server/runtimecommand`, avoiding a package cycle. The admitted queue returns the opaque ordered-mutation dispatcher bound into the Engine and is retained directly by the `agentResource`; do not route this lifecycle through `registry.RuntimeRegistry` or add a second fan-out owner.
- Each admitted queue owns one joined worker, the transient command-stage permit state machine, permit-backed output continuations for genuinely deferred external work, and one small start gate per atomic handoff; it does not own a generic side-effect scheduler. The start gate has only waiting/committed/aborted outcomes and cannot launch work itself. Existing owners remain the structured parents:
  - an idle user turn, user shell command, or manual/pre-submit compaction uses `sessionruntime.StartAgentExecution` directly instead of the waiting `RunCurrentAgentExecution` convenience; the returned `ExecutionHandle` is registered before its Runner passes the start gate;
  - Engine lifecycle work uses `launchLifecycleTask`, whose wait-group registration happens before its task passes the gate;
  - each local tool/process child increments the existing `executeToolCalls` wait group and starts a goroutine blocked on the gate before its tool-start mutation;
  - provider and compaction work that runs synchronously inside an already registered Agent execution needs no child owner: the Agent `ExecutionHandle` remains its parent.
  Every admitted Agent Exact Execution Scope receives one root output continuation before its Runner can pass the gate. A Runtime Command-started execution transfers the command's permit. A Workflow/lifecycle-started Agent execution with no originating Runtime Command acquires one ordinary permit before owner registration, then binds it to the returned exact scope while the Runner is still gated. Child provider, foreground tool/process, compaction, Agent-scope lifecycle work, and each Step/Turn-boundary Pending Work claim reuse that root continuation only while the Agent scope remains live. Automatic after-Turn Queue follow-up runs as another Agent Turn inside that same `ExecutionHandle`, Exact Execution Scope, Runner, and root continuation; it never launches a resource-lifecycle task, creates a successor scope, or acquires a new root permit. The scope owner keeps the continuation valid through every accepted same-scope Queue follow-up and Goal continuation, then releases the permit and retires the scope exactly once after the final continuation stage reaches its terminal outcome. Script execution and finalization never acquire a Session-queue permit, gate, continuation, baseline, or fence.
- For an idle `SubmitUserTurn`, separate the submitted-turn result from execution termination. Before atomic handoff, its adapter creates one typed `SubmittedTurnResult` milestone plus the private scope-terminal continuation. The initial submitted Agent Turn's ordered final-result stage completes that milestone exactly once with the existing `RuntimeSubmitUserTurnResponse` assistant/error after its authoritative output commits and before the same Runner receives a committed after-Turn claim result that can start Queue follow-up. `ExecutionHandle.Wait` remains the private lifecycle join for the whole same-scope execution and is never the service-response boundary. Later automatic Queue or Goal continuation keeps the handle, scope, and permit owned without changing the completed milestone; if the Runner fails before producing it, terminal cleanup completes it with the same originating command error.
- Split the shell ownership transition at the actual return boundary:
  - `shell.Manager.Start` no longer invokes the global event handler for transition-to-background. It returns a typed background outcome containing the immutable transition payload and an opaque manager-owned pending-transition token. Terminal publication for that process waits for token commitment or abortion;
  - `ExecCommandTool` only formats the model-facing result and attaches the typed outcome as opaque transient metadata on `tools.Result`; it has no dispatcher, continuation, or Session mutation dependency. The token is abort-on-exit while formatting, and successful return atomically transfers token ownership to runtime. The metadata is not serialized, persisted, or provider-visible;
  - `runtime.defaultToolExecutor` is the sole consumer and result owner. It finalizes presentation, then submits one Agent-continuation stage containing the transition event and stored tool completion as one atomic steering batch. The pending token is abort-on-exit until that stage returns a typed commit result;
  - if the stage did not commit, the runtime applier aborts the token: `shell.Manager` suppresses terminal publication, performs graceful then forced kill/join with the existing bounded process policy, removes the entry, and runtime returns the joined steering/cleanup error. If the stage committed, runtime commits the token with an infallible ownership transition. A post-commit notification error is surfaced once with the committed receipt; runtime preserves the process and committed tool result and never retries or aborts them;
  - after `Start` or `WriteStdin` returns, `shell.Manager` is the sole long-lived process owner. Each later `EventCompleted`/`EventKilled` callback runs independently in the manager's completion path and routes by captured owner Session and resource generation through a typed Session-resource `BackgroundShellUpdate` command that acquires an ordinary permit when the event arrives. Waiting there cannot block the already-returned tool call from applying its result and freeing capacity.
  A post-return notice-suppressed update completes and releases immediately. A terminal notice transfers that same permit into one pending resource-scoped notice entry, so the scheduler stores permit-backed typed entries rather than unbounded bare messages. At idle, the scheduler deterministically batches its bounded pending entries into one `BackgroundNoticeDrain` stage at the then-current tail: one leader permit transfers to the gated Engine lifecycle continuation, while follower permits remain batch-owned until their own notice applies or reaches a typed non-application result. Full capacity therefore needs no fresh permit to drain. Resource close fails all pending entries and releases their permits. No capacity is retained during the background process lifetime.
- At most one gate and one pending re-entry slot exist per retained permit. Different Session queues have independent workers and share no execution lock. Resource draining closes external admission and wakes background-event admission waiters with the existing unavailable outcome, lets accepted commands and registered continuations reach their command-specific terminal outcome, joins the worker and Engine lifecycle owners, and only then closes the Engine. The process-global shell manager remains outside the Session queue and retains its existing server-shutdown ownership.

### Typed command and queue model

- Represent command targets as explicit variants:
  - a Session-resource target captures the admitted `SessionResourceRef`;
  - an Agent Exact Execution target captures a `sessionruntime.ExecutionScope` only after validating `Kind() == ExecutionScopeAgent` and obtaining its non-absent `SessionResourceRef`, including resource and execution generations.
  Commands that are scoped only to the Session use the first variant; agent Goal changes, live Agent Workflow completion, foreground tool/runtime results, and any other Agent-scope-sensitive operation use the second. A Script scope is rejected at this adapter boundary and stays in the Workflow domain. Do not encode target absence with empty IDs.
- Keep public and adapter call sites typed. Each command family has an immutable command payload and typed result. A package-level generic submit helper may erase commands only into a private queue-stage interface; its typed future/result channel is created before erasure and completed exactly once. The queue never switches on strings, API route names, `client_request_id`, or untyped maps to determine behavior.
- A queue stage produces one of two sealed outcomes:
  - **complete**: return the command's typed result and release its command-stage permit; for Live Steer and Queue input, this is the accepted result produced after the ordered Pending Work append, not later model delivery;
  - **continue**: transfer the same permit to a registered output continuation while resource-parented external work runs.
  A continuation has exactly one reusable re-entry slot. Dispatch changes its permit from continuation-idle to continuation-pending, appends one typed mutation/result stage at the queue's current tail under the queue mutex, and waits for that stage to apply before the slot becomes idle again. Concurrent child producers sharing one continuation wait on that slot. A typed public-milestone stage may complete the command family's existing response future and return the continuation to idle without releasing its permit; the later private terminal stage uses the same slot to complete lifecycle ownership and release the permit. Re-entry receives a new FIFO sequence every time and never keeps the original sequence or a placeholder node.
- Make the transition from a prerequisite authoritative mutation to external work one atomic typed handoff, not two independently drainable submissions:
  1. create a queue-owned start gate and register the existing structured owner with its Runner/task/process blocked on that gate; registration failure returns before any Session mutation;
  2. under the queue lifecycle mutex, contend with draining to reserve the permit-backed continuation for that already registered owner;
  3. if reservation wins, apply the prerequisite mutation in the current queue turn, commit the continuation, invalidate the turn, and open the gate; if draining wins or mutation fails, abort the gate and join the no-work owner.
  Owner registration may expose only its existing internal queued lifecycle state; it cannot call a provider, start a process, emit a Session mutation, or publish a tool start before the gate opens. Resource draining sees and joins the owner even during the reservation race. Drain win means typed failure with no prerequisite mutation or external work. Reservation win means draining sees both the owner and continuation. Mutation failure aborts both and work never starts. The handoff must never expose committed input or a tool-start record without an owned continuation.
- Bound each Session's transient Runtime Command stage backlog with an implementation-constant capacity and pre-stage-admission backpressure; do not add a queue-full DTO, public setting, rejection contract, priority lane, or completion lane. A stage enters the Runtime Command FIFO only after its caller acquires a command-stage permit. The permit has one state machine—externally queued/running, continuation-idle, continuation-pending/running, or released—and authorizes at most one queued/running stage at a time. Engine mutations emitted by accepted external work reuse their parent's continuation slot and never acquire another stage permit. Consequently, even when every permit belongs to deferred external work, each owner can enqueue and await one intermediate mutation, reuse the slot for later mutations, and finally enqueue its terminal result. Standalone Engine work without a parent continuation must acquire an ordinary permit before it starts. Total command stages remain bounded by the permit count.
- Live Steer and Queue input use capacity only transiently. After request validation, each submission acquires a command-stage permit and enters the same Session Runtime Command FIFO. In its FIFO turn, the input adapter revalidates the target and Completion Fence, copies the immutable text and identity into the existing authoritative Engine Pending Work FIFO, publishes the existing accepted state, completes the existing acceptance response, and releases the stage permit immediately. The accepted Pending Work item retains no Runtime Command permit, continuation, placeholder stage, or fixed-count capacity. Pending Steer and Queue storage therefore has no fixed count ceiling; each busy composer `Enter` can submit another item without waiting for an earlier item's model delivery. Queue-item acceptance and discard use their own short-lived stages. Automatic Queue follow-up acquires no new permit or owner: it reuses the originating live Agent root continuation after the submitted-turn milestone. Explicit `SubmitQueuedUserMessages` delivery may retain only its own delivery-command permit after it atomically registers the Agent execution that will return its existing terminal response; it never inherits a permit from an accepted Pending Work item.
- Delivery is separate from acceptance, and the delivery boundary is itself ordered. At the next safe Agent Step for Steer, or after the Agent Turn for Queue, the Engine appends one typed `PendingWorkDeliveryClaim` stage through the live Agent continuation without first reading, snapshotting, selecting, marking, or draining Pending Work. The stage's FIFO position is the exact boundary cutoff: acceptance and discard stages ahead of it affect this boundary, while acceptance and discard stages behind it affect a later boundary.
- In the delivery-claim stage's FIFO turn, the Engine revalidates the captured Agent Exact Execution Scope, resource generation, boundary kind, stopped state, and command-specific eligibility. A single shared claim applier then uses a typed selector—boundary-specific eligible prefix, explicit IDs, or the existing all-pending policy—to identify the currently eligible Pending Work and commit its removal, combined flush persistence, statuses, and existing applied/failed receipt as one ordered operation. No selected item, text, or removal leaves the applier before that turn's commit result. A non-committed flush leaves every item in its original FIFO position; a committed flush removes each item exactly once. The Pending Work FIFO remains authoritative storage, while the Runtime Command FIFO alone orders acceptance, discard, claim, and delivery.
- A committed automatic after-Turn Queue claim returns control to the existing Agent Runner, which starts the queued next Agent Turn under the unchanged Exact Execution Scope and root continuation. When that turn ends, the Runner appends another after-Turn claim and repeats. A no-work claim does not itself retire a scope that still has an existing Goal continuation. If neither Queue nor Goal continuation remains, the no-work claim and scope-finishing transition linearize under the queue lifecycle mutex: an input acceptance ahead of the claim is consumed by it, while a stage behind it observes finishing/fenced state and is rejected rather than becoming accepted work stranded after the final claim.
- Separate caller waiting from command execution. The request context controls validation, command-stage permit acquisition, and pre-stage-admission waiting only. After the Runtime Command FIFO appends the stage, execution uses the admitted resource/server lifecycle and completes even if the request, connection, or subscriber disappears. A still-connected caller may await the typed future; existing operation reconciliation and memo wrappers observe that future but never own its ordering.

### Mutation execution and re-entry

- Reuse `server/runtime/output_steering.go` as the typed leaf mutation model. Wrap its existing `steeringIntent` batch in an opaque runtime ordered-mutation value whose application remains inside `runtime.Engine`; do not create a parallel transcript/event mutation pipeline. Replace `outputMutationMu` as an inter-command ordering mechanism with dispatch through the admitted Session queue. Leaf locks may remain only where they protect data structure integrity inside one applied turn.
- Give the Engine a narrow ordered-mutation dispatcher bound before its Session resource becomes Ready. Bind each admitted Agent Exact Execution Scope to its parent single-slot output continuation; resource lifecycle work binds a Session-resource continuation. Keep the queue-turn capability lexical rather than storing it in a context, Engine field, or async closure:
  - the worker invokes a stage with an opaque turn value valid only for that synchronous callback;
  - synchronous command appliers explicitly require the turn to apply nested steering inline without re-enqueueing;
  - the queue invalidates the turn before the callback returns control to the worker, and any later/cross-Session use returns a diagnostic typed error and fails fast in debug;
  - deferred/provider/foreground-process/tool work receives only its dispatcher and live Agent continuation, never the turn; every non-streaming authoritative effect serializes through that continuation's one pending slot, appends at the then-current tail, and awaits application;
  - the runtime shell-result applier receives the opaque transition metadata and still-live Agent continuation from the executing tool call; post-return terminal shell events and notice steps receive only their captured Session-resource target or resource-scoped lifecycle continuation. A transition payload that cannot use its live Agent continuation returns a typed non-commit result and fails fast in debug; a terminal event that attempts to reuse the retired continuation is likewise diagnostic;
  - existing `e.steer` producers remain behind one central dispatcher seam instead of propagating a turn/context through all producer call sites;
  - line-by-line Markdown commentary/final streaming stays on its specified direct transient path, while stream finalization, committed assistant output, tool lifecycle, runtime notices, history replacement, and other durable/model-visible effects use the queue.
- Keep long provider, process, filesystem-preparation, and similar Session work outside the worker. Reuse `sessionruntime.StartAgentExecution`/`ExecutionHandle`, Engine lifecycle tasks, local tool wait groups, and the process-global `shell.Manager` as their existing structured owners. The queue start stage validates and captures immutable inputs, starts or registers the applicable owner, and returns control to the worker. Agent-scoped result stages revalidate the captured Session resource and Agent Exact Execution Scope; background stages revalidate only the captured Session resource generation. Script handles remain wholly outside this authority. Short authoritative persistence operations, such as an event-log append or the final bounded database transaction, remain in the result/application stage.
- Split operations only at existing typed seams. In particular:
  - compaction computes provider/local output outside the queue and applies history replacement plus completion/failure publication through a typed result stage;
  - shell/process work uses the atomic handoff to pair its tool-start mutation with an existing wait-group child blocked on the start gate, then uses the parent execution continuation for ordered tool/process results;
  - the runtime tool executor atomically applies the Manager-returned background transition and stored tool completion through the live Agent continuation without nested admission, then commits or aborts the manager token from the typed commit receipt; later `BackgroundShellUpdate` and `BackgroundNoticeDrain` commands target the captured Session resource generation and never the retired scope;
  - an idle accepted human input starts an `ExecutionHandle` whose Runner waits on the gate, atomically pairs input commit with that registered owner, and completes a typed submitted-turn milestone after the first Agent Turn without waiting for handle termination. A busy-turn Steer or Queue copies its immutable item into authoritative Pending Work in its FIFO command turn, returns at that existing accepted boundary, and releases its transient stage permit. At the required Agent Step or Agent Turn boundary, runtime appends a typed claim stage through the still-live Agent continuation without touching Pending Work first; only that stage's ordered turn may claim, persist, remove, and apply the eligible items. A committed automatic Queue claim loops within the same Runner/scope, while the already completed first-turn milestone remains unchanged;
  - provider/compaction work starts only after its registered Agent Runner's gate opens; all of its non-streaming steering effects reuse that execution continuation rather than consuming nested permits;
  - model `complete_node`, structured/unstructured Agent completion, and agent-facing Workflow service completion call one queue-aware live-Agent Workflow completion adapter, which delegates the final exact-scope transaction to `CurrentNodeController`;
  - Script finalization and unambiguous idle Workflow completion continue to call the existing Workflow controller directly, with no Session queue dependency;
  - Goal commands retain the existing dormant direct path, while every live path submits through the Session queue.

### Command-family result ownership

- Runtime Command stage admission is the internal FIFO append after pre-validation and command-stage permit acquisition. It creates no generic public accepted/result DTO. Every command has exactly one command-family adapter as result authority. For Live Steer and Queue input, product acceptance linearizes later in that stage's FIFO turn when the immutable item enters authoritative Pending Work; the existing public acceptance future and transient stage permit both complete there, before model delivery. For another immediate command, the adapter's typed future completes at its existing applied result and releases the stage permit. For an atomic-handoff command, the same adapter owns the existing public result milestone plus one private typed terminal continuation; this is not a second public command result or a second mutation owner. In particular, idle `SubmitUserTurn` completes `SubmittedTurnResult` after its first turn while the private continuation can remain owned by automatic Queue or Goal work. The table states which milestone returns the service call and which continuation releases a retained permit. Each milestone completes at most once. `runtimeops` and request memos may observe the named family milestone and copy its outcome into their existing records, but they never wait for `ExecutionHandle` termination, resolve the milestone, apply mutation, or release capacity.

### Completion Fence linearization

- Maintain one queue-owned per-Agent-Exact-Execution input-acceptance generation and fence state; do not duplicate the fence in a client, Workflow store row, Script scope, or runtime read model.
- Create an immutable Completion Attempt under the queue mutex before live Agent completion-producing work begins. It captures the Agent Exact Execution Scope and current input generation: the provider turn captures it before the request that can yield model/tool/structured completion, and an agent-facing Workflow service completion captures it at command admission. A completion result carries that original baseline when it re-enters; re-entry never refreshes it. Script and idle Workflow completion have no Completion Attempt or Fence.
- In the input stage's FIFO turn, input acceptance checks the fence and target under the queue lifecycle mutex and, if open, atomically increments the generation and appends the immutable item to authoritative Engine Pending Work. The adapter then publishes acceptance and releases its transient stage permit. Every input accepted after a Completion Attempt begins therefore invalidates that attempt whether acceptance occurs before or after result re-entry; a stage merely waiting for capacity or its FIFO turn is not yet accepted. Relative to a delivery-claim stage, an acceptance turn ahead of the claim is eligible at that boundary, while an acceptance turn behind the claim remains pending for the next boundary; no goroutine may establish that cutoff by reading Pending Work early.
- When that completion result reaches its turn, it revalidates the Agent Exact Execution Scope and attempts to acquire the Completion Fence under the queue mutex:
  - input accepted after the attempt baseline but before result re-entry has already changed the generation, so completion is superseded even if that input has not yet applied;
  - input accepted after result re-entry but before the fence attempt also changes the generation, so completion is superseded without Workflow mutation;
  - if the completion fence transition wins the mutex first and the generation is unchanged, the scope becomes fenced and later input is retryably rejected before append, restoring its draft and never reaching a successor.
- The live-Agent Workflow completion adapter owns the fence lease. A successful final transaction commits it until Agent Exact Execution Scope retirement; a non-final command-specific failure aborts the lease while the same Agent scope remains live. Tests must force both mutex orders and the result-reentry gap rather than relying on timing.

### Background notice ownership

- Replace the scheduler's raw pending slice and boolean drain/consume contract with typed owned entries keyed by the existing background process/session identity. An entry carries its immutable notice intent, captured Session resource, retained permit, typed future, and one state variant: pending, claimed by standalone drain, claimed by combined user flush, batch-owned, applying, applied, not-applied-after-prior-failure, suppressed by completion harvest, failed, or canceled. Terminal entries are removed. Do not represent ownership with parallel booleans or let callers receive bare `[]steeringIntent`.
- Standalone scheduling, `FlushPendingUserInjections`, and completed-`write_stdin` harvesting contend under the same scheduler mutex:
  - standalone scheduling claims a deterministic pending batch but does not make it irrevocable until `BeginApply`;
  - inside the ordered Pending Work delivery-claim turn, combined user flush may claim pending background-notice entries and return a typed owned batch. Under the same Agent continuation and lexical turn that flushes the user messages, `BeginApply` atomically transfers surviving notice entries into batch ownership, applies their intents in scheduler order, and resolves each future/releases each permit only after that entry's ordered application or typed non-application failure;
  - completion harvesting replaces `ConsumePendingBackgroundNotice(... ) bool` with a typed suppression result. It suppresses and releases a matching pending or claimed-but-not-applying entry exactly once. If `BeginApply` already won, harvesting reports already-applying/applied and never releases or mutates that entry.
- `BeginApply` is the notice ownership linearization point. It rechecks all claimed entries under the scheduler mutex, removes entries already suppressed/failed, elects a surviving standalone leader if needed, and transfers survivors to one bounded batch before any steering mutation. Thus harvesting can cancel a claim before mutation, but cannot race a batch-owned/applying notice into a second release. Standalone and combined flush cannot both own one entry.
- A standalone batch uses one surviving leader permit to register and gate the resource lifecycle notice step. Follower permits move to an explicit batch-follower capacity state and authorize no independent queue stage; follower futures remain unresolved. The batch contains at most one entry per retained permit, so merging capacity ownership does not create an unbounded lane. Before steering begins, task registration/cancellation failure resolves every survivor with that typed outcome and releases all permits.
- Apply standalone and combined batches entry-by-entry in scheduler order. After one notice mutation succeeds, resolve that entry successfully and release its follower permit. The leader entry future may also resolve then, while its permit changes to resource-lifecycle-owner and remains retained until the lifecycle task terminates. If steering fails on entry N, resolve entries before N successfully, resolve N with the steering failure, mark every later entry not-applied due to that same prior failure without invoking its mutation, and release all corresponding follower permits. The leader lifecycle permit releases when the task exits. No entry future resolves successfully merely because a process-local batch copied its intent.
- If no entry survives `BeginApply`, no task starts and every terminal entry is already released. Resource drain/shutdown transitions every pending, claimed, batch-owned, or not-yet-applied entry to its typed failure/cancellation, preserves already-applied success, and releases each remaining capacity lease once.

### Validation, failure, and cutover invariants

- Keep request DTO validation and command-specific preconditions before command-stage capacity acquisition. Stage admission then captures the Session-resource or Agent-scope target. Immediately before application, resolve that captured target through `sessionruntime.Authority` and revalidate current Session, resource generation, Completion Fence/closing state where applicable, Agent Exact Execution Scope where applicable, Agent Step/Turn boundary, and command-specific assumptions. A stale command completes through its existing typed failure/notification path without invoking its mutation.
- Retain `runtimeops.Coordinator` and `requestmemo` temporarily as command-specific reconciliation/result observers required by KENT-346. Place their commit/cancellation checks inside the relevant typed command stage where required, but do not use their operation keys, barriers, memos, or retry records to choose Session order or queue identity.
- Remove or narrow every competing Session mutation lane after its producers use the queue: direct `withRuntime` mutation paths, the live-steer fallback lane, direct live-Agent Workflow completion calls, direct live Goal execution, background event/notice steering, and Engine output ordering via `outputMutationMu`. Keep direct Script/idle Workflow completion and mutexes or exact-live gates that enforce local atomicity, prompt identity, lifecycle control, or data-race safety; verify none can independently reorder two accepted Runtime Commands.
- After an idle submitted-turn milestone completes, the same `ExecutionHandle`, Exact Execution Scope, resource pin, root continuation, and permit remain owned while an after-Turn claim or queued follow-up is pending/running. Live Stop/Interrupt in the gap targets that exact owner; stop-first prevents the queued provider turn, completes the queued item through its existing failed/stopped path, and then permits one terminal release without changing the already returned first-turn result. A retirement request records closing/cancellation but cannot retire the resource or create a successor until that owner reaches its terminal stage. Claim/follow-up-first remains bound to the same scope, then observes any later stop/closing state at its next ordered boundary.
- Queue shutdown never transfers pending work to a successor generation. New submissions observe the existing unavailable/closing or retryable Completion Fence behavior. Resource retirement and an appended delivery-claim stage contend at the queue lifecycle boundary: retirement-first makes the claim stage remove or deliver nothing, then the resource-close owner applies the existing typed failure cleanup to remaining Pending Work; a committed claim-first result completes against that exact resource before closure. Neither outcome can target a successor. The final no-work claim/continuation decision, scope retirement, and permit release complete once; an input stage behind that final decision is rejected instead of becoming accepted work. Accepted Pending Work keeps its command-owned cancellation and restart semantics without retaining stage capacity; genuinely deferred external completion can always re-enter with its retained permit, and event publication remains unconditional on subscriber count.
